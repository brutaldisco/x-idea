# ADR-026: 動画ダウンロードの書き込み使い回しと CDN URL 再取得

- 日付: 2026-09-17
- 状態: 採用
- 関連: ADR-007、ADR-021、ADR-023、ADR-025、設計書 8 章（SC-15）/ 14.6

## 文脈

ハートビート（ADR-025）の記録から、2 つの構造的な問題が判明した:

1. **大きなファイルで急激に遅くなる**。3 件がすべて 2.7〜2.8GB あたりで
   停止していた。原因はプロキシ逐次経路の `writeChunkToFile` が
   チャンク（4〜32MB）ごとに `createWritable({ keepExistingData: true })`
   を開き直していたこと。Chrome のこの API は `keepExistingData: true`
   のとき既存ファイル全体を一時ファイルへコピーしてから書き込むため、
   2.7GB のファイルに 4MB を書くたびに 2.7GB のコピーが走っていた。
   CDN 直接経路（`downloadDirectToFile`）は writable を 1 回だけ開く
   ためこの問題はなく、プロキシ逐次だけが抱えていた。
2. **502 で失敗したとき同じ経路でしかリトライしない**。CDN URL は
   ダウンロード開始時に 1 回だけ取得し、CDN 直接が失敗するとプロキシに
   落ち、プロキシが 502 を返しても同じ URL・同じ経路でリトライするだけ
   だった。URL の取り直しや経路の切り替えがなかった。

## 決定

1. **プロキシ逐次でも writable を 1 回だけ開いて使い回す**。
   `writeChunkToFile`（file handle 受け取り・毎回開閉）を
   `writeChunkToWritable`（開き済み writable 受け取り）に変え、
   `downloadVideoFile` のプロキシ逐次ループの前に 1 回だけ
   `createWritable` する。リトライ時は `writable.seek(start)` で
   位置を戻して上書きする。
2. **`refreshDirectUrl` コールバックで CDN URL を取り直す**。
   `downloadVideoFile` の本体を `runOnce` として切り出し、
   リトライ可能なエラー（5xx・429・ネットワーク断）で失敗したとき、
   1 回だけ URL を取り直して CDN 直接からやり直す。
   これにより「CDN 一時障害」「プロキシ 502」「URL 失効」のすべてに
   対応できる。
3. **5xx のバックオフを長めにする**。502 はサーバー側の回復に時間が
   かかるため、5xx の場合は最大 30 秒（従来は最大 10 秒）まで
   指数バックオフで待つ。

## 影響

- プロキシ逐次経路で大きなファイルが途中から急激に遅くなる問題が
  解消する（createWritable の全コピーが 1 回で済む）。
- 502 などの一時障害で失敗しても、URL を取り直して CDN 直接から
  書き込み済み位置の続きを再開できる。
- `refreshDirectUrl` は 1 回だけなので、恒久的な障害で無限ループに
  なることはない。

## 改定（2026-09-20: 大きな途中ファイルの 0 B/s ループ）

再開時に保存済み位置を最初の `onProgress` で出すと、スタール監視が
武装して 75 秒で `createWritable` を切っていた。4GB 超の
`keepExistingData` 全コピーは 75 秒では終わらず、開き直しを繰り返して
0 B/s のまま固まる。再開カーソルの最初の進捗では監視を武装せず、
開き直しのタイムアウトは既存サイズに応じて最大 15 分まで延ばす。
コピー中はハートビートだけ送り、別タブが割り込まないようにする。
256MB 以上の途中ファイルは、CDN 直接が止まったあとにプロキシへ
落とさない。プロキシは全コピーをもう一度やり、Vercel 経由の残り取得で
また応答なしになる。代わりに CDN URL を取り直して直接経路を 1 回だけ再試行する。

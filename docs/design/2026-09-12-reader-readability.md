# 設計書：Reader 本文の読みやすさ改善

- 日付: 2026-09-12
- 状態: **採用（T-220 / T-221 実装）。T-222（見出し推定）は未実装**
- 関連: 実装設計書 8.6 / 10.2 / 10.4、T-207、ADR-006、`docs/design/2026-09-07-multilingual-chrome-translate.md`
- きっかけ: 長文の X 投稿を Reader で開くと文字の壁になって読み進められない（2026-09-12、スクリーンショット）

## 1. 目的

Reader の本文（原文・記事・要約・Chrome 翻訳結果）を、**長文でも上から下まで読み切れる組み**にする。文字を増やさず、余白と幅と階層だけで直す。原文の文字列は 1 文字も変えない。

## 2. 現状（2026-09-12 時点の実装の実測）

PC（`min-[48rem]` 以上、ビューポート 1024px）での本文幅は次のとおり。Reader は `AppChrome wide` なので外枠は `max-w-4xl`（896px）。

| ブロック | 実装 | 本文幅 | 字サイズ / 行送り | 行間比 | 1 行の全角字数 |
| --- | --- | --- | --- | --- | --- |
| 原文 `PostBlock` | `whitespace-pre-wrap text-[1.05rem] leading-7`、カード `p-5` | 896−48−40 = **808px** | 16.8px / 28px | **1.67** | **約 48 字** |
| 記事（テキスト）`ArticleBlock` | `whitespace-pre-wrap text-sm leading-7`、カード `p-4` | 896−48−32 = **816px** | 14px / 28px | 2.00 | **約 58 字** |
| 記事（HTML）`ArticleBlock` | 同上 ＋ `[&_p]:my-2` | 816px | 14px / 28px | 2.00 | 約 58 字 |
| 要約 `source/[id]/page.tsx` | `text-sm leading-7`、カード `p-5` | 808px | 14px / 28px | 2.00 | 約 58 字 |
| Chrome 翻訳結果 `ChromeTranslate` | `whitespace-pre-wrap text-sm leading-6` | 約 780px | 14px / 24px | 1.71 | 約 56 字 |

日本語 1 段組の推奨は **35〜45 字/行**。PC ではすべて超えている。

スマホ（375px）は原文で約 19 字/行。こちらは狭いほうに寄っているが実害は小さく、今回の対象外とする（5.2 参照）。

すでに入っていて効いている設定（触らない）：`globals.css` の `font-feature-settings: "palt"`、`text-wrap: pretty`、`line-break: strict`、`hanging-punctuation: allow-end`、`body { line-height: 1.75 }`。

## 3. 読みづらさの原因（影響の大きい順）

### 3.1 段落が見えない（最大の原因）

原文・記事テキスト・要約・翻訳結果はすべて **1 つの `<p>` に `whitespace-pre-wrap`** で流している。したがって

- 原稿の単一改行（`\n`）＝ **余白ゼロの改行**
- 折り返された行 ＝ **同じく余白ゼロ**

となり、**「折り返しの続き」と「次の段落」が見分けられない**。X の長文投稿や note 系の原稿は「1 文 1 行」で書かれることが多いので、本文全体が等間隔の行の塊になる。スクリーンショットがまさにこれで、`一覧に載っているのは…上のようになります。` が 2 行に折り返した直後に `単語だけでも通ります。…` が同じ間隔で続くため、どこで話が変わったのか目で追えない。

空行（`\n\n`）があるところだけ 1 行分（28px）空くが、それは原稿に空行があるときだけで、本文の大半には無い。

HTML 記事側も `[&_p]:my-2` = 8px しかなく、**行送り 28px より段落余白が小さい**。段落として認識できない。

### 3.2 1 行が長い

2 章のとおり PC で 48〜58 字。行末から次の行頭へ目が戻る距離が長く、行を 1 つ飛ばす・同じ行を読み直すが起きる。3.1 と重なると「どこを読んでいたか」を完全に見失う。

### 3.3 見出しが本文と同じ見た目

スクリーンショットの `なぜ単語ひとつで絵柄が変わるのか` は原稿上の見出しだが、プレーンテキストなので**本文と同じ字形・同じ間隔**で出る。章の切れ目が無いので、長文が 1 本の帯になる。

### 3.4 sticky バーが半透明で本文が透ける

`ReaderSegments` は `sticky top-0 z-10 bg-paper/90 backdrop-blur`。90% 不透明 ＋ blur なので、**スクロール中の本文がバーの下に薄く見える**。スクリーンショット上部でも文字がバーに滲んで、直下の行が切れて読めない状態になっている。

### 3.5 行長に対して行間が狭い（原文）

原文は 48 字/行で行間比 1.67。長い行では 1.8〜1.9 ないと行を追えない。記事は 2.0 あるが字が 14px なので別問題（3.6）。

### 3.6 記事本文・要約が 14px

長文を読ませる面に `text-sm`（14px）を使っている。原文は 16.8px なので、**同じ Reader の中で本文の大きさが 2 種類**あり、記事タブに入った瞬間に読む姿勢が変わる。設計書 10.2 は「本文 16px/1.75」と書いてあり、実装がどちらも一致していない。

### 3.7 本文リンクのコントラスト不足

`LinkedText` は `text-accent/55 underline decoration-accent/30`。`--color-accent` は `oklch(55% 0.16 250)` なので、55% の不透明度で紙色に載せると実効 `oklch(74%)` 相当、コントラストは約 2.5:1。設計書 10.4 の「コントラスト AA（4.5:1）」を満たさない。`break-all` も、URL には妥当だが日本語混在行で不自然な位置に折り返しが入る。

### 3.8 ダークの本文コントラストが高すぎる（任意）

ダークは `--color-ink: oklch(96%)` / `--color-paper: oklch(18%)` で約 15:1。長文では白が滲む（ハレーション）。12:1 程度に落とすほうが読みやすい。優先度は低い。

## 4. 非目標

- AI で見出しを付ける・要約を増やす・本文を書き換える。**原文カラム（`x_posts.text` / `articles.content_*`）は読むだけ**で、表示の組み方だけを変える。DB にも何も書かない。
- 有料トグルを触る。`user_id` を足す。全件 SELECT。
- Reader の外枠を `max-w-3xl` に戻す（T-218 の並列ルートで Library と共有する前提なので `max-w-4xl` は維持し、本文だけ内側で絞る）。
- 2 段組・縦書き・ページめくり。
- 記事 HTML の再サニタイズ方針の変更（ADR の範囲外）。

## 5. 改善案

### 5.1 段落を作る（P0・本丸）

プレーンテキストを**行ごとのブロックに分けて `<p>` で出す**。純粋関数を切り出してテストする。

`src/lib/reader-paragraphs.ts`（新規）

```ts
export type ReaderLine = {
  text: string;
  /** 直前に空行があった。大きめの間を開ける */
  breakBefore: boolean;
  /** 箇条書き・番号付きの行。前後を詰める */
  bullet: boolean;
};

export function splitReaderLines(text: string): ReaderLine[];
```

規則：

1. `\r\n` / `\r` を `\n` に正規化し、`\n` で分割。各行の末尾空白を落とす。
2. 空行は捨て、**直後の非空行に `breakBefore: true`** を付ける。連続した空行はまとめて 1 つ扱い。
3. `^\s*(?:[-*・･●○◆▶▼>»]|\(?\d{1,2}[.)）]|[①-⑳])\s` に当たる行は `bullet: true`。
4. 残りの非空行は **1 行 = 1 段落**。
5. 全体が空なら空配列（呼び出し側は従来のフォールバック文言を出す）。

余白（`em` 基準なので字サイズ設定に追従する）：

| 位置 | 余白 |
| --- | --- |
| 先頭 | 0 |
| 段落間 | `0.8em` |
| 空行のあと（`breakBefore`） | `1.8em` |
| 箇条書きが連続する間 | `0.2em` |

**段落余白（0.8em ≈ 13px）が行送りの差として効くかどうかが要点**なので、行間を詰めずに余白を足す。行送り 31px ＋ 段落余白 13px で、折り返しと段落が明確に分かれる。

「1 文 1 行」の原稿では段落数＝文数になり縦に伸びる（スクリーンショットの範囲で +250px 程度）。読み切れるほうを取る。

適用先（4 箇所で同じレンダラを使う）：

- `PostBlock` の本文と引用ブロック
- `ArticleBlock` のテキスト版本文
- `source/[id]/page.tsx` の AI 要約
- `ChromeTranslate` の翻訳結果ペイン。Translator は改行を潰すので、渡す前に行間を空行にし、表示は `splitReadableLines`（長い一行は句点でも段落化）を使う。

実装上の注意：

- `id={textId}` と `translatableProps` の `lang` / `translate` は、`<p>` ではなく**包む要素に移す**。`ChromeTranslate` の `selectElementText` は `getElementById` した要素のテキストを Range で選ぶので、中が複数 `<p>` でも動く。翻訳に渡す文字列は DOM ではなく props の生テキストなので影響なし。
- `LinkedText` は行ごとに呼ぶ。`splitHttpUrls` の `offset` を key に使っているので、行内オフセットで衝突しないよう行番号を key に混ぜる。
- コピー結果が `\n` から `\n\n` に変わる。許容する。

### 5.2 本文幅・字サイズ・行間を 1 つに揃える（P0）

`globals.css` に本文用のクラスを 1 つ置き、4 箇所から使う。

```css
.reader-measure {
  line-height: 1.85;
  max-width: 40em;      /* 全角 40 字。em なので字サイズ設定に追従 */
}

.reader-body {
  font-size: 1.05rem;   /* 16.8px。原文の現状値を正式値にする */
  line-height: 1.85;    /* ≈31px */
  max-width: 40em;      /* ≈672px */
}
```

- **`max-width: 40em`** が 3.2 の答え。`rem` や `px` ではなく `em` にして、設計書 10.2 の「文字サイズ設定 15/16/17/18px」を将来入れても 40 字のまま保つ。
- 外枠 `max-w-4xl` は維持し、本文だけ内側で絞る。本文はカード内で中央（`margin-inline: auto`）。PC のカード左右パディングは `2rem`（ヘッダー・翻訳ボタン用）。メディアギャラリー・引用・バッジはカード幅のまま。
- 記事本文の 14px を 16.8px に上げる（3.6）。設計書 10.2 の「16px」は実装に合わせて **16.8px（1.05rem）** に直す。
- **AI 要約は例外**。3 行要約の短いメタブロックなので、幅の上限（`40em`）と行間（1.85）だけ当て、**字サイズは `text-sm` のまま**にする。ここを本文と同じ大きさにすると、`bg-ai-soft` のカードが原文より目立って読む順番が崩れる（設計書 10.1 の「AI 生成物は色で区別」の意図を壊す）。クラスは `.reader-measure`（`max-width` ＋ `line-height` のみ）として分け、`.reader-body` はそれに字サイズを足したものにする。
- スマホ（375px）は `40em` に届かないので自動的に今と同じ全幅。設計書 8.6 の「モバイルは左右パディングを詰めて本文幅を広げる」はそのまま有効。

HTML 記事（`article-body`）も同じクラスを当て、段落余白を行送りより大きくする：

- `[&_p]:my-2`（8px）→ `[&_p]:my-[0.8em]`
- `[&_h1]`/`[&_h2]` に上余白 `1.8em` ＋ 下余白 `0.3em` ＋ サイズ差（`h1` 1.3em / `h2` 1.15em）を付け、本文と区別する。今は `font-semibold` と `mt-3`/`mt-4` だけで階層が見えない。
- `[&_li]:my-[0.2em]`、`[&_blockquote]` に左罫線を付ける。

### 5.3 sticky バーを不透明にする（P0・1 行）

`ReaderSegments` の `bg-paper/90 backdrop-blur` → **`bg-paper`（不透明）**。下罫線はすでにある。これで 3.4 の透けが消える。`sticky top-0` とセクションの `scroll-mt-16`（64px）はバー実高（約 52px）より大きいので、アンカージャンプ側は変更不要。

### 5.4 見出しらしい行を少し立てる（P2・任意）

プレーンテキストの原稿に階層を戻す。誤検出しても**表示の太さが変わるだけ**（文字は変わらない、DB にも書かない）なので害は小さいが、確信度の高い条件に絞る。

`splitReaderLines` の戻り値に `heading: boolean` を足し、次のすべてを満たす行だけ `true`：

- 空行の直後、または本文先頭
- 30 字以下
- 句読点（`。！？.!?`）で終わらない
- 箇条書きでない、URL だけでない
- **直後の行が本文らしい**（40 字以上、または句点で終わる）

表示は `font-semibold` ＋ 上余白 `1.8em` ＋ 下余白 `0.3em`。サイズは上げない（上げると誤検出が目立つ）。

スクリーンショットの `なぜ単語ひとつで絵柄が変わるのか` は「空行直後ではない」ため、この条件では拾えない。条件を緩める（空行直後を必須にしない）かどうかは、実データ 20 件で誤検出率を見てから決める。**緩めた版を既定にするのは、誤検出が 1 割を切ってから**。

### 5.5 本文リンク（P1）

`LinkedText`：

- `text-accent/55 decoration-accent/30` → **`text-accent decoration-accent/50`**（4.5:1 を満たす）。薄くしたい意図が t.co の抑制なら、色ではなく `text-sm` 相当のサイズ差か短縮表示で解く。
- `break-all` → `[overflow-wrap:anywhere]`。日本語の行中に不要な分断を作らず、長い URL のはみ出しも防ぐ。

### 5.6 ダークの本文色（P2・任意）

`--color-ink` をダークで `oklch(96%)` → `oklch(90%)`。約 12:1 で AA を十分満たす。全画面に効くのでダークの目視確認をセットにする。

## 10. 本体設計書との差分（採用時に直す）

- **10.2 タイポグラフィ**：「本文 16px/1.75」→ 実装に合わせて **本文 1.05rem（16.8px）/ 1.85、本文幅は `max-width: 40em`（全角 40 字）**。「文字サイズ設定 15/16/17/18px」は未実装のまま（`html { font-size: 16px }` 固定）だが、`em` 基準にしておけば後から入れて追従する。
- **8.6 Reader**：原文・記事・要約は**段落として組む**（単一改行も段落として扱い、空行はより大きな区切り）ことを追記。「モバイルは左右パディングを詰めて本文幅を広げる」は維持。
- **10.4 アクセシビリティ**：本文リンクを含めて AA を満たすことを明記（現状 `LinkedText` が未達）。
- 原文の扱い：**表示の組み方は変えるが原文カラムは読むだけ**。AGENTS.md の「原文カラムを AI が書き換えない」に抵触しないことを 8.6 に一言添える。

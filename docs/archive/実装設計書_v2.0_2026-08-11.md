## 1. プロダクト概要

Xでブックマークした投稿を自動的に収集し、AIが要約・分類・タグ付け・関連付けを行うことで、「保存して終わり」ではなく「必要なときに引き出せる」個人用ナレッジデータベースを構築するWebアプリケーション。

コアコンセプトは以下の3点である。

1. **ユーザーの操作はXでのブックマークだけ。** 収集・解析・整理はすべて自動。ユーザーが能動的に行うのは「確認・修正・活用」のみ。
2. **原文（Source）と自分の知識（Knowledge Card）の分離。** 外部から取得した一次情報と、それをもとに自分の言葉で整理した知識を、データ構造・UIの両面で明確に区別する。
3. **AIは提案者、人間は決定者。** AIの判定は確信度付きで保存され、確信が高ければ自動確定、低ければInboxで少数の候補を提示する。人間の修正は常にAIの再処理より優先される。

対象プラットフォームはモバイルファーストのレスポンシブWebアプリ（PWA対応）。**本人1人だけのシングルテナント**として設計する。マルチユーザー・公開SaaS化は将来拡張にも含めない（必要になったら別プロダクトとして再設計する）。

## 2. 目的と成功条件

### 2.1 目的

- Xのブックマークが「読み返されない墓場」になる問題を解消する。
- 学習テーマ（社会学、AI、仕事、筋力トレーニングなど）ごとに知識が自動で蓄積・整理される状態を作る。
- 保存済みの情報に対して検索・質問・再利用ができ、複数の情報源から自分の知識（Knowledge Card）を構築できるようにする。
- **月額インフラ費用を原則ゼロ**にし、フリーミアム枠内で運用を完結させる。

### 2.2 成功条件（測定可能な形で定義）

| # | 成功条件 | 測定方法 | 目標値 |
| --- | --- | --- | --- |
| S1 | ブックマークが自動で取り込まれる | 同期成功率（直近30日） | 99%以上 |
| S2 | ブックマークからアプリ反映までの遅延 | 同期間隔＋処理時間 | 60分以内（既定の同期間隔30分の場合） |
| S3 | AI分類の自動確定率 | 自動確定数÷全取り込み数 | 70%以上（運用3か月後） |
| S4 | AI分類の修正率 | ユーザー修正数÷自動確定数 | 20%以下 |
| S5 | 保存情報が実際に引き出されている | 検索・質問・Source閲覧の週次利用回数 | 週5回以上（本人の実利用） |
| S6 | 運用コスト | インフラ＋AIは $0、X APIのみ従量 | **インフラ/AI $0**、X API **月$5以下**（通常運用） |
| S7 | Inbox処理の負担 | 要確認アイテムの1件あたり処理時間 | 10秒以内（スワイプ/1タップで完結） |
| S8 | フリーミアム枠内運用 | Turso / Vercel / Gemini の各枠超過有無 | 月次で超過なし |

S3/S4は運用開始後にプロンプトと確信度しきい値をチューニングするための指標であり、リリース時のブロッカーではない。

## 3. 想定ユーザーと利用シナリオ

### 3.1 想定ユーザー

- 本人（単一ユーザー）。Xを日常的に閲覧し、社会学・AI・組織・デザイン・筋力トレーニング・健康・仕事・思想などの投稿を1日数件〜数十件ブックマークする。
- スマートフォンでの利用が主。PCでは検索・Knowledge Card編集などの「じっくり作業」を行う。
- ログイン操作は不要。自分のデプロイ先URLを開いてそのまま使う。
- **[仮定]** 取り込み量は平均20件/日、ピーク50件/日、年間約7,000〜18,000件と想定する。コスト・性能の見積もりはこの規模を基準とする。

### 3.2 利用シナリオ

**シナリオ1：日常の収集（操作ゼロ）**
通勤中にXを閲覧し、ブルデューの文化資本に関する投稿と、AIエージェント設計の記事リンク付き投稿をブックマークする。30分後、アプリが自動同期し、投稿本文・リンク先記事を取得。AIが要約・分類（社会学/理論、AI/方法）・タグ付けを行い、確信度が高いためそのままライブラリに自動確定される。ユーザーは何もしない。

**シナリオ2：すきま時間のInbox確認（1〜2分）**
昼休みにアプリを開く。ホームに「新着12件（自動確定10件・要確認2件）」と表示される。Inboxを開くと、AIが分類に迷った2件だけが表示され、それぞれカテゴリ候補が3つ提示されている。1タップで確定し、1件は不要だったのでスワイプでアーカイブする。

**シナリオ3：知識の引き出し**
週末、筋トレメニューを組み直すために「週3回の筋力トレーニング 分割法」で検索する。キーワード＋意味検索で過去に保存した投稿・記事が根拠付きで一覧され、「まだ実践していない」状態のものだけに絞り込む。質問画面で「保存した情報の範囲で、初心者向けの週3分割の推奨は？」と質問すると、根拠となるSourceのリンク付きで回答が返る。

**シナリオ4：Knowledge Cardの構築**
「AIエージェントのモデル分担」について保存した5件のSourceをもとに、AIがKnowledge Cardのドラフト（タイトル、一文要約、重要ポイント、主張、根拠、注意点）を生成する。ユーザーは「自分にとっての意味」「次に試すこと」を自分の言葉で追記して保存する。AI生成部分と自分の記述はUI上で明確に区別されて表示される。

**シナリオ5：矛盾の発見（優先度2）**
「タンパク質摂取量」について新しく保存した投稿が、過去に保存した投稿と異なる主張をしているとAIが検出し、Source詳細に「矛盾の可能性がある情報」として関連表示する。

## 5. MVPの範囲

MVP（優先度1）は「**Xでブックマークするだけで、要約・分類済みの情報がモバイルで検索・閲覧できる**」を成立させる最小構成とする。

含まれるもの：

- X連携（F-02）。アプリログインは無し
- ブックマーク同期：定期（既定30分間隔）＋手動、差分取得、重複防止、削除・非公開・取得不能の状態管理（F-03/F-04）
- X投稿の保存：本文、投稿者、日時、URL、投稿内リンク、引用投稿（1階層）、メディアの基本情報（F-05/F-22）
- 外部記事の取得：メタデータ（タイトル・著者・公開日・概要・サムネイル）＋合法的に取得可能な本文（F-06）
- AI処理：要約、カテゴリ判定、タグ生成、情報タイプ判定、重要度推定。確信度に基づく自動確定／Inbox振り分け（F-07/F-08）
- 未整理Inbox、ライブラリ、Source詳細、キーワード検索、カテゴリ管理、同期エラー確認、設定（F-09〜F-15）
- モバイルファーストのレスポンシブUI（PWA：ホーム画面追加・基本的なオフライン閲覧）

MVPの完成条件（Definition of Done）は「32. 受け入れ条件」に記載。

## 6. MVPに含めない範囲

| 項目 | 除外理由 | 拡張余地の確保方法 |
| --- | --- | --- |
| アプリ認証・マルチユーザー | 個人用途のため不要 | シングルテナント前提。`user_id` 列は持たない |
| Knowledge Card（F-16） | Sourceの収集・整理が安定してから価値が出る | `knowledge_cards` 系テーブルはスキーマ設計済み（18章）。P2で有効化 |
| 意味検索・質問回答（F-17/F-18） | 埋め込み・RAGは追加クォータ消費がある | `source_chunks.embedding`（Turso vector）を最初から用意。P2でバックフィル |
| 重複・関連・矛盾検出（F-19） | 埋め込み基盤に依存 | `source_relations` テーブル設計済み |
| 定期レビュー・エクスポート（F-20/F-21) | 蓄積後に価値が出る | ジョブ基盤・データ構造で対応可能 |
| 画像OCR・動画文字起こし・フォームカード（F-23） | MVPを複雑化させる主要因のため明示的に除外 | `media_assets` に解析結果用のJSON列を確保 |
| 返信スレッドの収集 | 要件で明示的に対象外 | — |
| ネイティブアプリ／プッシュ通知 | PWAで代替。通知はP2以降に検討 | — |
| X以外の収集源（RSS、はてブ等） | スコープ外 | `sources.origin` 列で将来の収集源追加が可能 |
| Obsidian相当のグラフUI・双方向リンク編集 | 本製品の差別化ではない | Markdownエクスポート（F-21）で外部PKMへ逃がす |

## 7. 画面構成

画面は9つに絞る。「迷わない」ことを最優先し、下部ナビゲーションは5項目固定とする。

| 画面ID | 画面名 | 役割 | ナビゲーション位置 |
| --- | --- | --- | --- |
| SC-01 | ホーム | 新着サマリー、要確認件数、最近のSource、同期状態の要約 | 下部タブ1 |
| SC-02 | 未整理Inbox | AIが確信を持てなかったアイテムの確認・確定（スワイプ/1タップ） | 下部タブ2（バッジで件数表示） |
| SC-03 | ライブラリ | 全Sourceの閲覧。カテゴリ・情報タイプ・状態・タグで絞り込み | 下部タブ3 |
| SC-04 | 検索・質問 | キーワード検索（MVP）／意味検索・質問回答（P2）を1画面に統合 | 下部タブ4 |
| SC-05 | 設定 | 同期設定、X連携、カテゴリ管理への入口、データ管理 | 下部タブ5 |
| SC-06 | Source詳細 | 原文・要約の切替表示、分類編集、メモ、状態変更 | SC-01〜04から遷移 |
| SC-07 | Knowledge Card詳細（P2） | KC の閲覧・編集。AI生成部と自分の記述の区別表示 | SC-03/04/06から遷移 |
| SC-08 | カテゴリ管理 | 階層カテゴリの追加・変更・統合・並び替え | SC-05から遷移 |
| SC-09 | 同期エラー | 同期履歴・失敗理由・再試行 | SC-01/05から遷移 |

ログイン画面は存在しない。初回アクセス時、X未連携ならホームに「Xと連携」CTAを出す。

## 9. モバイルUI設計

- 下部固定タブ（5項目）。主要CTAは親指帯に置く。
- Inboxはカードスタック。右スワイプ＝確定、左スワイプ＝アーカイブ、タップ＝候補から選択。
- Source詳細：
  - 「原文」タブ：投稿本文の完全表示（引用投稿は入れ子カード）、元投稿へのリンク、メディアサムネイル。
  - 「記事」タブ：リンク先記事のリーダー表示（取得できた範囲）。取得状態（全文/一部/メタのみ）を明示。
  - 「要約」タブ：AI要約（AIバッジ付き）。
  - 下部固定バー：状態変更（未読/読了/実践予定…）、メモ追加、（P2）KC作成。
  - ユーザーメモはAI要約と視覚的に分離（枠線＋「自分のメモ」ラベル）。
- ダークモードは必須にしない（OS追従で十分）。装飾過多を避け、情報密度を優先。

## 10. 主要操作フロー

1. **初回セットアップ**：設定でX連携 → 初回同期ジョブ投入 → ホームに進捗表示。
2. **日常同期**：外部Cron → `/api/jobs/tick` → `sync_bookmarks` → `article_fetch` / `enrich_source` をキュー投入 → ワーカー消化。
3. **Inbox処理**：要確認のみ表示 → 1タップ/スワイプで確定。
4. **検索**：キーワード（MVP）→ ハイブリッド＋RAG（P2）。
5. **KC作成（P2）**：Source選択 → AIドラフト → 自分の記述を追記 → 保存。

```
│  └ /api/jobs/tick            │  Cronから叩かれるワーカー入口
└──────────────┬──────────────┘
               │ @libsql/client
┌──────────────▼──────────────┐
│  Turso Free（libSQL/SQLite） │
│  ├ アプリデータ               │
│  ├ FTS5（日本語キーワード検索）│
│  ├ vector（意味検索・P2）     │
│  └ jobs テーブル（キュー）     │
└──────┬──────────────────────┬───────┘
       │                      │
┌──────▼─────┐         ┌──────▼──────────────┐
│  X API v2  │         │  Google AI Studio    │
│  bookmarks │         │  Gemini Flash（無料） │
│  OAuth2    │         │  + Embedding（P2）   │
└────────────┘         └─────────────────────┘

外部Cron（無料）※ Vercel Hobbyの高頻度Cron制約を回避
  cron-job.org / GitHub Actions schedule 等
  → 毎分〜数分ごとに POST /api/jobs/tick（CRON_SECRET）
```

データフロー概要：

1. 外部Cron → `/api/jobs/tick`（共有シークレット）→ pending ジョブを最大N件処理。
2. `sync_bookmarks` が X API から差分取得 → `sources` / `x_posts` へ保存 → `article_fetch`・`enrich_source` を投入。
3. 同一 tick または後続 tick で記事取得・AI処理を消化。
4. クライアントは Next.js API 経由でデータを読み書き。認証レイヤなし（シングルテナント）。

## 12. 推奨技術スタック（フリーミアム）

### 12.1 推奨構成（結論）

| レイヤ | 採用技術 | 無料枠の位置づけ |
| --- | --- | --- |
| フロントエンド | **Next.js 15+（App Router, TypeScript）+ Tailwind CSS + shadcn/ui** | 開発体験・PWA化が容易 |
| ホスティング | **Vercel Hobby** | 個人非商用で $0。Preview/Production デプロイ |
| DB | **Turso Free**（libSQL / SQLite） | 5GB / 500M rows read / 10M rows written / 月。個人規模で十分 |
| ORM/クライアント | **Drizzle ORM + @libsql/client** | 型安全・マイグレーション容易 |
| 全文検索 | **SQLite FTS5**（unicode61。日本語はバイグラム／トライグラム補助） | 外部検索エンジン不要 |
| 意味検索（P2） | **Turso vector** + **Gemini Embedding**（無料枠） | 別ベクトルDB不要 |
| AI（要約・分類） | **Google Gemini Flash / Flash-Lite**（AI Studio 無料枠） | カード不要で開始可。クォータはAI Studioで確認 |
| ジョブキュー | **Turso上の `jobs` テーブル**＋外部Cronで tick | 専用キュー基盤不要 |
| Cron | **cron-job.org** 等の無料HTTP Cron、または **GitHub Actions** `schedule` | Vercel Hobbyの高頻度Cron制限を回避 |
| 監視 | アプリ内ヘルス（`/api/health`）＋任意で UptimeRobot 無料枠 | Sentryは任意（無料枠） |
| IaC/マイグレーション | Drizzle Kit（SQLをGit管理） | Turso CLIで適用 |

### 12.2 フリーミアム完結の原則

1. **有料必須は X API のみ**とみなす（Owned Reads の従量。13.5）。
2. インフラ（Vercel / Turso）と AI（Gemini）は無料枠内に収まる設計・運用を優先する。
3. 枠超過で止まるサービスがある（Turso Freeは超過時ブロック）。**インデックス設計とページネーションで rows read を抑える**ことを第一級の制約とする。
4. AI無料枠のレート制限に当たったらジョブを `run_after` 先送りし、課金へ自動エスカレーションしない。

### 12.3 代替案とトレードオフ

| 構成 | 利点 | 欠点 | 判断 |
| --- | --- | --- | --- |
| Supabase（旧案） | Auth/RLS/pgvectorが揃う | 本要件ではAuth不要。Free→Pro圧が強い | **不採用** |
| Cloudflare Workers + D1 | エッジ・Cron内蔵 | FreeのCPU 10ms制約がジョブ向きでない | 不採用（tickトリガー役なら可） |
| Anthropic Claude | 品質が高い | 無料枠が本用途の定常運用向きでない | 有料オプションとして設定切替可能に残す |
| ローカルSQLiteファイルのみ | 完全無料・最速 | スマホからの常時アクセス・Cron連携が弱い | 開発時の埋め込みレプリカ用途に留める |
| Meilisearch等の外部検索 | UX最高 | 別プロセス運用・無料枠管理が増える | FTS5で十分。将来の逃げ道のみ |

**トレードオフの明示**：SQLite/FTS5はPGroongaほどの日本語形態素解析は持たない。バイグラム補助＋タグ/カテゴリ完全一致でMVP品質を確保し、必要ならP2で意味検索を足す。Gemini無料枠はポリシー上、入力がプロダクト改善に使われる可能性がある（25章）。気になる場合は「AI一時停止」または将来の有料プロバイダ切替で対応する。

### 12.4 ローカル開発

- `turso dev` またはローカル libSQL / ファイルSQLiteで開発可。
- `.env.local` に `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN` / `X_*` / `GEMINI_API_KEY` / `CRON_SECRET` を置く。
- 本番と同じマイグレーションを適用する。

## 13. X連携方式

> **本章の事実関係は 2026-07-12 時点の docs.x.com（X API v2 OpenAPI 2.166）に基づく。** X APIの料金・制限は変更が多いため、実装着手時に必ず再確認すること（33章 R-01）。

### 13.1 前提となる公式APIの現状（調査結果）

- **料金体系**：2026年2月6日以降、新規開発者は**従量課金（pay-per-use）のみ**。無料枠は新規には存在しない。クレジットを事前購入し、リクエスト/リソース単位で消費する。
- **Owned Reads**：自分のアプリで自分自身のデータを読む場合、`GET /2/users/{id}/bookmarks` は **$0.001/リソース**（1,000件で$1）。本アプリはまさにこの条件に該当する。
- **重複課金の排除**：同一リソースは**24時間（UTC日）内は再課金されない**（ソフト保証）。
- **レート制限**：`GET /2/users/:id/bookmarks` は **ユーザーあたり180リクエスト/15分**。
- **認証**：OAuth 2.0 Authorization Code with PKCE の**ユーザーコンテキスト必須**。必要スコープ：`bookmark.read`、`tweet.read`、`users.read`、`offline.access`。
- **取得仕様**：`max_results` 1〜100。`pagination_token` でページ送り。取得できるのは認証ユーザー自身のブックマークのみ。

※ X APIは本構成で**唯一の定常有料依存**である。スペンディングリミット必須。

### 13.2 認証フロー設計（Xのみ。アプリログインなし）

```
[設定画面] 「Xと連携」ボタン
  → GET /api/x/oauth/start
      state / code_verifier をサーバー側（暗号化Cookieまたは一時テーブル）に保存
      → https://api.x.com/2/oauth2/authorize へリダイレクト
  → Xの同意画面 → redirect_uri (= /api/x/oauth/callback)
  → トークン交換 → GET /2/users/me
  → x_account テーブルに保存（シングルトン行）
```

- 同期ジョブ実行時に有効期限を確認し、失効していればリフレッシュ。
- リフレッシュ失敗は `x_account.status = 'reauth_required'` とし、ホームにバナー表示。

### 13.3 差分取得アルゴリズム

Bookmarks APIは「ブックマークした順（新しい順）」で返す。**前回同期時の先頭既知IDに到達したら打ち切る**。

```
sync_bookmarks():
  token = ensure_valid_token()
  known_head = settings.last_sync_head_tweet_id
  new_head = null
  pagination_token = null
  fetched = []
  loop (最大 MAX_PAGES=10。初回のみ引き上げ可):
    page = GET /2/users/:id/bookmarks ?max_results=100 & fields/expansions...
    if new_head is null: new_head = page.data[0].id
    for tweet in page.data:
      if tweet.id == known_head: goto done
      if tweet.id in DB: continue
      fetched.append(tweet)
    if page.meta.next_token is null: goto done
  done:
    upsert fetched → sources / x_posts / media_assets / source_articles準備
    enqueue article_fetch / enrich_source
    settings.last_sync_head_tweet_id = new_head
    sync_runs に結果を記録
```

注意点：

- 後から過去投稿をブックマークした場合も先頭に現れるため取りこぼさない。
- `x_posts.tweet_id UNIQUE` でUPSERT。
- 削除・非公開は応答 `errors` 配列から `sources.availability` を更新。
- 返信投稿は設定 `save_replies`（既定: 保存）に従う。
- 編集追跡はMVPでは行わない **[仮定]**。

### 13.4 同期頻度と手動同期

| 項目 | 設計 |
| --- | --- |
| 定期同期 | 既定30分間隔（設定で 15分/30分/1時間/6時間/手動のみ） |
| 手動同期 | ホームの同期ボタン。最短60秒間隔でサーバー側スロットリング |
| ワーカーtick | 外部Cronが **1〜5分間隔** で `/api/jobs/tick` を叩く（同期自体は設定間隔を尊重） |
| レート制限 | `x-rate-limit-*` を `sync_runs` に記録。429時は reset＋ジッターで再試行 |

### 13.5 API料金の概算

| シナリオ | 月額目安 |
| --- | --- |
| 通常運用（20件/日） | **$1〜3** |
| 初回全量（例: 5,000件） | 一時 **$5** |
| 上限想定（50件/日） | **~$4.5** |

Developer Consoleでスペンディングリミット（例: $10）を必ず設定する。

### 13.6 公式APIが利用できない場合の代替

| 代替案 | 評価 |
| --- | --- |
| Xのデータダウンロードからの手動補完 | 非常用のみ |
| 共有シート/URL手動登録 | 補助入力としてP2検討 |
| 非公式API/スクレイピング | **採用しない** |

## 14. 記事取得方式

### 14.1 対象と方針

X投稿の外部URLを対象に、**「合法かつ礼儀正しく取れる範囲だけ取る」**。

```
article_fetch(url):
  1. URL正規化（t.co展開、UTM除去、短縮URL解決・上限5）
  2. articles.normalized_url の重複確認
  3. robots.txt 確認 → 拒否なら metadata_only
  4. HTML取得（連絡先付きUA、15秒、最大3MB、text/htmlのみ）
  5. OGP/Twitter Card/JSON-LD からメタデータ
  6. Readability で本文抽出 → サニタイズHTML＋プレーンテキスト
  7. 短文/ペイウォール検出 → partial / metadata_only
  8. 保存後、必要なら re-enrich
```

### 14.2 `fetch_scope`

| 値 | 意味 |
| --- | --- |
| `full` | 本文全体 |
| `partial` | 一部のみ |
| `metadata_only` | 本文不可（ペイウォール/robots等） |
| `failed` | 取得失敗（再試行対象は一時エラーのみ） |

### 14.3 X内リンク

- 別X投稿：`x_posts` として保存し関係を記録。ブックマーク由来でなければ Source 化しない **[仮定]**。
- X Articles：取れる範囲で保存、不可なら `metadata_only`。
- 同一URLは `articles.normalized_url` で一意化。

### 14.4 著作権・規約への配慮

- 取得本文は本人の私的アーカイブ用途のみ。再配布・公開機能を持たない。
- robots / noarchive を尊重。
- 出典URLを常に表示。ドメイン除外リストを設定で持つ。

## 15. AI処理フロー

### 15.1 原則

1. **非同期**：収集とAIを分離。AI障害でも同期は止まらない。
2. **原文不変**：AIは原文カラムを書き換えない。
3. **人間優先**：`*_source='user'` はAI再処理で上書きしない。
4. **確信度駆動**：しきい値（既定0.80）で自動確定 / Inbox。
5. **監査可能**：モデル・プロンプト版・入出力トークンを `enrichments` に記録（無料枠でも件数把握のため）。
6. **無料枠優先**：既定プロバイダは Gemini。429/クォータ超過時は課金へ逃げず `run_after` を遅延。

### 15.2 enrichジョブ（MVP）

1回のLLM呼び出しで要約・分類・タグ・情報タイプ・重要度を取得。

```
入力:
  - 投稿本文・投稿者・引用
  - 記事タイトル＋本文先頭2,000字（取得済みなら）
  - 既存カテゴリツリー、頻出タグ上位100、情報タイプ定義

出力（JSON強制）:
  {
    summary, category_id?, category_confidence,
    new_category_suggestion?,
    tags[], info_type, info_type_confidence,
    importance: 1|2|3, language, reasoning
  }

後処理:
  - category_confidence ≥ 閾値 かつ category_id あり → auto_filed
  - それ以外 → needs_review（候補最大3）
```

使用モデル **[仮定]**：`gemini-2.5-flash-lite`（またはAI Studioで無料かつ安定している最新Flash系）。品質不足時のみ設定で Flash / 有料プロバイダへ切替。

### 15.3 P2で追加するAI処理

| 処理 | 方式 |
| --- | --- |
| 埋め込み | Gemini Embedding → `source_chunks.embedding`（Turso vector） |
| 重複/関連/矛盾 | 類似度しきい値＋LLM二次判定 |
| KCドラフト / QA | Flash（必要なら有料モデルへオプション） |
| 陳腐化検出 | 週次バッチ |

### 15.4 再処理・修正

- 「AIで再処理」ボタン。ユーザー確定フィールドは保持。
- プロンプトはリポジトリの `prompt_versions` で管理。

## 16. バックグラウンドジョブ設計

### 16.1 方式：Turso上のジョブテーブル＋HTTP tick

専用メッセージキューは導入しない。個人規模では十分。SQLiteは書き込み直列のため、`SKIP LOCKED` 相当は不要。楽観的な1件払い出しでよい。

```sql
-- 払い出し（単一ワーカー前提）
UPDATE jobs
SET status = 'running',
    started_at = datetime('now'),
    attempts = attempts + 1,
    locked_by = :worker_id
WHERE id = (
  SELECT id FROM jobs
  WHERE status = 'pending' AND datetime(run_after) <= datetime('now')
  ORDER BY priority DESC, created_at
  LIMIT 1
)
RETURNING *;
```

### 16.2 ジョブ種別

| type | 内容 | トリガー | 優先度 | 目安タイムアウト |
| --- | --- | --- | --- | --- |
| `sync_bookmarks` | 差分同期 | 設定間隔到達時に tick が投入 / 手動 | 100 | 120秒 |
| `article_fetch` | 記事取得 | sync完了時 | 50 | 60秒 |
| `enrich_source` | AI整理 | sync/記事取得完了時 | 40 | 90秒 |
| `embed_source`（P2） | 埋め込み | enrich完了時 | 30 | 60秒 |
| `relate_source`（P2） | 関連検出 | embed完了時 | 20 | 90秒 |
| `weekly_review`（P2） | レビュー | 週次 | 10 | 300秒 |

### 16.3 実行モデル

- **起動**：外部Cronが1〜5分毎に `POST /api/jobs/tick`（`Authorization: Bearer CRON_SECRET`）。
- **1 tickの仕事量**：最大N件（既定3〜5）。Vercel Hobbyの実行時間内に収める。重い処理はジョブを細かく割る。
- **同期間隔の尊重**：tickのたびに同期するのではなく、`settings.sync_interval_min` と `last_synced_at` を見て `sync_bookmarks` を投入する。
- **再試行**：指数バックオフ（`1m * 2^attempts`、最大5回）。恒久エラーは `failed_permanent`。
- **ゾンビ回収**：`running` のままタイムアウト超過した行を `pending` に戻す（tickの冒頭で実施）。
- **直列化**：`sync_bookmarks` は同時に1本のみ（statusまたは簡易ロック行）。

### 16.4 Cron配置の推奨

| 手段 | 用途 |
| --- | --- |
| cron-job.org（無料） | 本番の `/api/jobs/tick` 呼び出し（推奨） |
| GitHub Actions `schedule` | リポジトリ運用と一体で回したい場合 |
| Vercel Cron | Hobbyは高頻度に向かないため補助扱い |

## 17. データモデル

### 17.1 設計方針

- **Source と Knowledge Card の分離**を最上位原則とする。
- **AI出力とユーザー入力の分離**（`ai_*` / `user_*`、`*_source`）。
- **原文の不変性**。
- **シングルテナント**：`user_id` を持たない。設定・X連携はシングルトン。
- **SQLite型**：UUIDはTEXT、真偽はINTEGER 0/1、時刻はISO8601 TEXT、JSONはTEXT、ベクトルはTursoのBLOB/vector型。
- **rows read 抑制**：一覧はカーソルページネーション必須。フィルタ用インデックスを最初から張る。

## 18. テーブル定義

```sql
INSERT INTO settings (id) VALUES (1);
```

## 21. 検索設計

### 21.1 キーワード検索（MVP）

FTS5を主、タグ/カテゴリ名の完全一致を補助。

| 対象 | 重み |
| --- | --- |
| 投稿本文 | 高 |
| 記事タイトル | 高 |
| ユーザーメモ | 高 |
| AI要約 | 中 |
| 記事本文 | 中 |
| タグ・カテゴリ | 完全一致優先 |

日本語クエリは **スペース分割＋文字バイグラム展開**をアプリ層で行い、FTS5に渡す **[仮定]**。フィルタ（カテゴリ・情報タイプ・状態・タグ）はAND。

### 21.2 意味検索（P2）

Turso vector の近傍検索。クエリも同一埋め込みモデル。

### 21.3 ハイブリッド（P2）

キーワード上位と意味検索上位を **RRF（k=60）** で統合。

### 21.4 QA（RAG、P2）

```
質問 → ハイブリッド上位チャンク
     → Gemini に「保存情報のみ根拠。不足なら不足と言う。[n]引用」
     → citations を保存・表示
```

性能目標：キーワード 500ms以内、ハイブリッド 1s以内（SQLite個人規模）。

## 22. Knowledge Card生成方式

### 22.1 原則

AIフィールドとユーザー記述フィールドは別カラム。AIはユーザー欄に書かない。UIでも分離表示。

### 22.2 生成フロー

1. Source選択（関連候補を提示、最大10）。
2. AIドラフト（title / one_liner / key_points / claims+evidence）。
3. ユーザーが意味・活用・次アクションを記入。
4. 保存し、Sourceの `read_status` を `knowledged` に。

### 22.3 更新

- 再生成はAIフィールドのみ。ユーザー記述は保持。
- `contradicts` 関連がある場合は注意バナー。

## 23. エラー処理

| ID | エラー | 対応 | ユーザー通知 |
| --- | --- | --- | --- |
| E-01 | X API 429 | resetまで待機・再試行 | なし |
| E-02 | Xトークン失効 | `reauth_required`、同期停止 | ホームバナー |
| E-03 | X 5xx/ネットワーク | バックオフ→sync_runs失敗 | 連続失敗時SC-09 |
| E-04 | 削除/非公開 | availability更新 | Source詳細 |
| E-05 | 記事404/410 | failed（恒久） | 記事タブ |
| E-06 | 記事一時失敗 | 再試行 | 表示のみ |
| E-07 | ペイウォール/robots | metadata_only | 「概要のみ」 |
| E-08 | Gemini 429/クォータ | run_after遅延。**課金へ自動切替しない** | 処理待ち表示 |
| E-09 | AIスキーマ不一致 | 1回再試行→needs_review | Inbox |
| E-10 | ジョブゾンビ | tick冒頭で回収 | — |
| E-11 | Cron未実行 | 最終同期監視 | ホームに最終同期 |
| E-12 | Xクレジット不足 | 同期停止 | バナー |
| E-13 | Turso枠超過 | 書き込み失敗を検知、ホームに警告 | 「DB枠を確認」 |

実装規約：外部呼び出しは `withRetry`。トークンをログに出さない。ユーザー文言は「何が起きたか＋次にできること」。

## 24. 運用上の注意（セキュリティ最小）

個人用途・強いセキュリティ不要を前提に、**事故りにくい最小セット**だけ置く。

### 24.1 やること

- X OAuthトークン・APIキーは**サーバー環境変数またはDBのサーバー専用カラム**にのみ置き、クライアントへ返さない。
- `/api/jobs/tick` は `CRON_SECRET` 必須。
- 記事HTMLは保存時にサニタイズ（XSSで自分のブラウザを壊さないため）。
- 依存更新は Renovate/Dependabot 任意。

### 24.2 やらないこと（意図的に省略）

- アプリログイン / OTP / RLS / 多要素認証
- トークンのアプリケーション層AES再暗号化（環境変数保護で足りる）
- WAF、IP制限、監査ログ基盤、SOC2相当の対策
- マルチテナント認可テスト

### 24.3 デプロイURLについて

VercelのURLは推測されうる。気になる場合のみ `APP_PASSWORD` オプション（20.3）を有効化する。ローカルまたはプライベート利用が主なら未設定でよい。

| A-07 | ユーザー修正は再enrich後も保持 | 再処理 |

- QAに引用が付く。根拠不足を明示。一般知識は分離表示。
- KCでAI部と自分の記述が分離され、再生成で消えない。
- エクスポートMarkdownに出典URLが含まれる。

## 付録B：AIプロンプト設計（enrichの骨子）

```
system:
あなたは個人用ナレッジデータベースの司書である。入力されたX投稿（および
リンク先記事）を、ユーザーの既存分類体系に従って整理する。
規則:
1. 要約は日本語3行以内。原文にない情報・意見を加えない。
2. カテゴリは必ず提示された既存カテゴリIDから選ぶ。適合が弱い場合は
   null とし new_category_suggestion に提案を書く。勝手に新設しない。
3. タグは既存タグを優先し、新規タグは一般名詞に正規化する（1〜5個）。
4. confidence は「同じ入力を10回分類したとき同じ結果になる確率」の見積り。
5. 出力はJSONスキーマに厳密に従う。

user:
## 投稿
author: {author_name} (@{username})
posted_at: {posted_at}
text: {text}
{quoted: 引用投稿があれば}
## リンク先記事（取得済みの場合）
title / author / 本文先頭2000字
## 既存カテゴリ（id: パス — 説明）
{category_tree}
## 既存タグ（頻出上位100）
{tags}
## 情報タイプ定義
theory=理論・概念 / method=方法・考え方 / procedure=手順 / research=研究・データ /
case=事例 / opinion=意見 / counter=反論 / tool=ツール / quote=引用・名言 /
idea=アイデア / news=ニュース
```

## 付録C：フリーミアム枠の前提

実装・運用時にダッシュボードで必ず再確認すること（数値は変動しうる）。

| サービス | 想定プラン | 本アプリでの使い方 | 注意 |
| --- | --- | --- | --- |
| Turso | Free | 正本DB、FTS、vector、jobs | 超過でブロック。INDEX必須 |
| Vercel | Hobby | Next.jsホスト | 商用・高頻度Cronは向きにくい |
